Building a Reusable AI-Assisted Documentation System

Organizing recurring standards, source checks, and task-specific instructions into reusable components for documentation work.

Anonymized production work for a U.S. healthcare IT product. Company, product, customer, and internal ticket identifiers are omitted.

Context​

Recurring documentation tasks required the same context each time: product terminology, source-of-truth rules, repository conventions, screenshot requirements, review steps, and content-type-specific guidance. Re-supplying that context manually for every AI-assisted task was inconsistent and added its own overhead.

Constraints​

The system had to use real product sources rather than infer missing facts. Different tasks also needed different rules: proofreading is not fact-checking, a screenshot workflow is not a writing workflow, and source conflicts need to be surfaced rather than silently resolved.

My role​

I organized recurring documentation rules into reusable Claude Skills and supporting utilities, including shared writing standards, Knowledge Base authoring guidance, Diátaxis/frontmatter checks, proofreading, fact-checking, screenshot preparation, and specialized UX microcopy guidance.

Approach​

I split the system into a shared standards layer and bounded task-specific components. The common layer carries terminology, voice, formatting, and linking rules. Task-specific Skills handle narrower jobs such as structure, factual verification, screenshot preparation, and UX copy.

The key design principle is that AI can collect, compare, restructure, and prepare material, but conflicting sources and publication decisions remain visible human review points.

Technical implementation​

The workflows connect Claude / Claude Code with Jira, Confluence, Figma, repository content, and existing documentation. The screenshot workflow uses Python utilities for image measurement and annotation. Fact-checking requires positive source verification and distinguishes an error from something that simply could not be verified.

Collaboration​

The components encode existing documentation standards and product-source practices rather than replacing subject-matter review. I use them inside the team's normal product and documentation workflow and update them as our working practices change.

Result​

Recurring documentation rules and task-specific instructions became reusable components instead of context that had to be rebuilt for each task. In one product-overview rework, the article went from 196 to 71 source lines, 14 to 5 H2 sections, and 14 screenshots to one orientation-focused visual.

What I learned​

AI is most reliable in documentation when the task is bounded, the source hierarchy is explicit, and the workflow says what to do when evidence conflicts or is missing.
